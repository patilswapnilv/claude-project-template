# DevRel Content Skill

Turn technical work into content developers actually read and share.

## Before writing, establish:
1. **The thing:** What is the feature/concept/release?
2. **The format:** LinkedIn post | blog intro | Twitter/X thread | README section | changelog entry
3. **The reader:** Junior devs | senior engineers | decision makers | open-source contributors
4. **The action:** What should they do after reading? (Try it, star it, share it, apply)

## Format guides

### LinkedIn post
- Hook in line 1 — no preamble, no "I'm excited to share"
- Lead with the problem, not the solution
- Concrete before abstract — show code or a specific example
- Max 3 paragraphs before "read more" fold
- End with one clear call to action
- Hashtags: 3-5, relevant, at the end

### Twitter/X thread
- Tweet 1: the hook — make someone stop scrolling
- Tweets 2-N: one idea per tweet, build progressively
- Every 3 tweets: a concrete example or code snippet
- Last tweet: summary + link
- Max 8 tweets for a thread — longer is not better

### Blog intro (first ~300 words)
- Open with the problem in context — put the reader in the situation
- State what they'll learn / be able to do by the end
- One concrete teaser: "By the end, you'll have X that does Y"
- No background section — get to the point

### README section
- H2 heading that answers "why does this exist"
- One-paragraph description — what it is, what problem it solves
- Quickstart: working code in under 10 lines
- Link to full docs

## Voice principles (generic — adapt to project voice)
- Write for the person who's busy and skeptical
- Concrete before abstract, always
- Show don't tell — working code > description of code
- No hype words: "revolutionary", "game-changing", "supercharge"
- One idea per sentence
- Active voice
